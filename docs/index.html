Secure agent workspace · developer guide

Per-call authorization on the Red Hat MCP Gateway

Stand up Kuadrant's MCP Gateway with Authorino on OpenShift, then put an IBM policy service behind it so that every single tool call an AI agent makes is exchanged, evaluated, and credentialed before it reaches a backend. From an empty namespace to a proven end-to-end path, with a validation checkpoint after every step.

OpenShift 4.19 mcp-gateway v0.7.1 Tech Preview AuthConfig v1beta3 RFC 8693 exchange RFC 9396 RAR Path proven live 2026-08-10

The composed architecture

Two vendors, one request path, and a strict division of labor. Red Hat's MCP Gateway (a Kuadrant project, shipped Tech Preview in the Red Hat Operators catalog) does discovery, federation, routing, and tool curation. It does not do per-call authorization, and it is not trying to: its three CRDs carry no reference to token exchange or rich authorization requests. The seam is Authorino, Kuadrant's ext_authz service, which the MCP Gateway operator pulls in as a dependency. Authorino authenticates the caller, calls out to an IBM policy service mid-request, gates on the returned decision, and injects the released credential into the upstream call.

Red Hat enforces the verdict; IBM makes it. This is a policy-enforcement-point versus policy-decision-point split, not a handoff of the authorization itself. Keep that framing: the composition never replaces the policy service, and the policy service never becomes a fork of the gateway.

Who owns what

How to read this guide

Every step ends in a checkpoint, and the checkpoint is always an evidence string, never a status word. An HTTP 200 proves nothing by itself; a seeded database cell string-matched in a tool result proves the whole path. This discipline came from the POC that this guide is built on: its probe recorder writes whatever verdict the author passes it, so the team learned to trust only the captured output. Adopt the same posture. Run the checkpoint, read the output, and only then move on.

Three rules recur through the guide, so here they are once:

  • Every positive needs a negative. A gate that has never refused anything is indistinguishable from no gate. Most checkpoints below pair an allow with a deny.
  • An empty result is not evidence without a positive control. When a grep is supposed to come back empty (and one checkpoint below depends on exactly that), first prove the grep finds things when they exist.
  • Keep secrets off command lines. Bearer tokens travel in environment variables or files; anything typed into argv ends up in captures, shell history, and pod specs.
Where this comes from

Everything here was proven live on an OpenShift 4.19.38 cluster in August 2026: manifests in deploy/rhgw/ (files 00 through 11), probes RHGW-P1 through P11 and HITL-P3, and decision records D2, D9, D10, and D11 tracked alongside them. Names like the mcp-gateway-demo namespace, the your-tenant.verify.ibm.com tenant, and the gateway.internal hostnames are that build's own example values; substitute your own consistently.

Run the platform gate

Sources: scripts/check-prereqs.sh · docs/runbook.md §1

Start with a go/no-go check, not with manifests. The gate is read-only and answers one question: can this cluster and workstation support the build at all? You need an OpenShift cluster at 4.16 or later (the POC ran 4.19.38), cluster-admin, and a workstation with the full toolset the gate verifies: oc, vault, helm, jq, curl, Node 20+, and podman or docker.

bash
cp env/poc.env.example env/poc.env   # fill in tenant URL, kubeconfig, registry
bash scripts/check-prereqs.sh

One of the gate's own checks is worth knowing by name, because you will reuse it when access drifts later, along with the runbook's version print:

bash
# the gate's C1: are you actually cluster-admin, not just logged in?
oc auth can-i '*' '*' --all-namespaces

# from runbook section 1: confirm the cluster version (the gate compares it to 4.16 itself)
oc version -o json | jq -r .openshiftVersion
Validate before you continue

The gate prints a per-check verdict and exits non-zero on any failure. oc auth can-i must print yes. If the gate passes but you changed clusters recently, re-run it: it is cheap, and every later step assumes its answers.

Learned live

Run every probe script in this guide with bash, never zsh. The POC's probe recorder refuses other shells outright because under zsh its timeout helper fails silently and probes get recorded as passing without ever running. That exact failure happened once before the guard existed.

1

Stand up the supporting services

Sources: deploy/base/ · deploy/vault/ · scripts/bootstrap-vault.sh · docs/runbook.md §5-§11

The gateway composition sits on services that are each their own install: this guide keeps them to one step with pointers, because the gateway path is the subject here. You need four things running before step 2 matters:

  1. Namespaces and the egress allowlist. oc apply -k deploy/base creates the workload namespace (here mcp-gateway-demo) with a default-deny NetworkPolicy baseline for agent pods. The namespace enforces the restricted Pod Security Standard, so every pod you create later needs runAsNonRoot, a seccomp profile, no privilege escalation, and all capabilities dropped.
  2. Vault Enterprise with the verify-rar plugin. Helm-install Vault (pin the fully qualified image docker.io/hashicorp/vault-enterprise: RHCOS resolves unqualified names against registry.connect.redhat.com first and the pod lands in ImagePullBackOff), create its Route, then run bash scripts/bootstrap-vault.sh to configure Kubernetes auth, SPIFFE issuance, and the verify-rar OAuth resource-server objects.
  3. An IBM Verify tenant with a token-exchange application per agent tier and the RAR types declared (scripts/configure-rar-types.sh). One application per tier is structural, not cosmetic: the act claim is a static per-application value, and RFC 8693 may_act names exactly one actor.
  4. Thin MCP servers and images. For a first build, deploy/rhgw/07b-mock-backends.yaml ships self-contained mock Databricks, Jira, and GitLab MCP servers (inline Node.js on a public UBI image, nothing to build). Real upstream MCP servers replace them later, and for those the cluster's internal registry must be enabled to hold your built images (TechZone clusters ship it Removed).
Do not learn this one live

After any vault-0 restart, copy the verify-rar plugin binary into the pod before unsealing. Unsealing with the plugin absent leaves the mount's storage read-only, and the lockup hides: reads and mints keep working, and nothing fails until the next role or config write. Neither a plugin reload nor moving the mount clears it.

Validate before you continue

Vault reports unsealed the way the repo's own scripts check it (oc exec -n vault vault-0 -- vault status -format=json | jq .sealed must print false), bash scripts/probe-netpol.sh proves the allowlist in both directions (a reachable allowed target and a refused disallowed one), and the internal registry accepts a push. The one input you can defer: the model API key, which only the agent runtime needs, not the gateway path.

6

Wire Envoy to Authorino (ext_authz)

Manifest: deploy/rhgw/05-extauthz.yaml

This is the seam. Envoy calls Authorino over gRPC ext_authz for every matched request, and Authorino runs the AuthConfig: authenticate, call out, authorize, inject. The wiring is not an EnvoyFilter: it is the same Istio CR from step 4, re-declared with an extension provider added to meshConfig. Applying it updates the one object.

yaml · 05-extauthz.yaml (the added block)
    meshConfig:
      extensionProviders:
        - name: authorino
          envoyExtAuthzGrpc:
            service: authorino-authorino-authorization.mcp-gateway-demo.svc.cluster.local
            port: 50051
            includeRequestBodyInCheck:
              maxRequestBytes: 65536
              allowPartialMessage: false
              packAsBytes: false

includeRequestBodyInCheck is what makes per-call MCP authorization possible at all. The tool name and its arguments ride in a JSON-RPC POST body; without the body, a policy can only decide on path and caller, which is the difference between an authorization gateway and a routing proxy. allowPartialMessage: false means a body over the 64 KB cap fails the check rather than being authorized on a prefix: closed, not truncated.

One object, two files

02-istio-cr.yaml and 05-extauthz.yaml define the same Kubernetes object. Apply 05 after (or instead of) 02, never 02 after 05: re-applying 02 silently removes the extension provider, oc apply reports "configured" either way, and the only symptom is that authorization stops happening.

Validate before you continue
bash
oc apply -f deploy/rhgw/05-extauthz.yaml
oc get istio default -o yaml | grep -A4 extensionProviders   # provider present

Nothing enforces yet: the provider exists but no AuthorizationPolicy activates it on any route. Step 7 creates the initial binding (mcp-gw-extauthz, scoped to /echo*) alongside the spike's AuthConfig, and step 10 extends that same object to the MCP path.

Prove the callout seam with a spike

Manifests: deploy/rhgw/04-spike.yaml · deploy/rhgw/06-authconfig.yaml · probe: scripts/probe-rhgw-callout.sh

Before putting the real policy service in the loop, prove the mechanism with a stand-in. The spike is one small Deployment with two endpoints: /policy pretends to be the callout (it returns a decision and fake credential fields), and /echo pretends to be a thin MCP and reports the headers it actually received, so header injection is observed rather than assumed. It runs as an inline Node.js server on a public UBI image, so there is nothing to build or push. An HTTPRoute maps /echo through the Gateway so there is a data path to protect.

Two applies. The AuthConfig's manifest also carries the initial ext_authz binding (the AuthorizationPolicy mcp-gw-extauthz, scoped to /echo* for now); without that binding nothing would call Authorino at all:

bash
oc apply -f deploy/rhgw/06-authconfig.yaml   # AuthConfig mcp-callout + the /echo*-only AuthorizationPolicy
oc apply -f deploy/rhgw/04-spike.yaml        # spike Deployment + Service + /echo HTTPRoute
One object, two files: apply 06 before 09, never after

Step 10's manifest re-declares this same AuthorizationPolicy extended to /echo* and /mcp*, and owns it from then on. Re-applying this step's file afterward reverts the rule to /echo* only, oc apply reports "configured" both times, and the MCP path silently loses authorization while every object looks healthy. That exact failure happened live in the build this guide is drawn from.

The AuthConfig is your first look at the four-stage shape everything later reuses. Read it top to bottom as a pipeline:

yaml · 06-authconfig.yaml
apiVersion: authorino.kuadrant.io/v1beta3
kind: AuthConfig
metadata:
  name: mcp-callout
  namespace: mcp-gateway-demo
spec:
  hosts:
    - mcp-gw-istio.mcp-gateway-demo.svc.cluster.local
    - mcp-gw-istio.mcp-gateway-demo.svc
  authentication:
    anonymous:
      anonymous: {}            # deliberate scaffolding: isolates the callout mechanism.
                               # The production config uses jwt (step 11).
  metadata:
    policy:
      http:
        url: http://rhgw-spike.mcp-gateway-demo.svc:8080/policy
        method: GET
        contentType: application/json
        headers:
          Accept:
            value: application/json
  authorization:
    allowed:
      patternMatching:
        patterns:
          - selector: auth.metadata.policy.decision
            operator: eq
            value: allow
  response:
    success:
      headers:
        x-db-password:
          plain: { selector: auth.metadata.policy.credential }
        x-granted-scope:
          plain: { selector: auth.metadata.policy.scope }
Learned live

Never set hosts: ["*"]. A wildcard claims every host on the gateway, and any later AuthConfig for the MCP path reports "No hosts linked to the resource" with no hint that another AuthConfig took the hostname. Narrow every AuthConfig to the hosts it owns.

Now the two-sided checkpoint, which is the pattern for everything that follows. Positive: a request through the gateway reaches the echo upstream carrying headers whose values were produced by the callout. Negative: patch the AuthConfig to require a decision the callout does not return, and the same request must die with 403. Without the negative, you have only shown that headers can be set, not that the callout gates anything.

bash · RHGW-P4 (positive)
# from any in-cluster pod:
curl -sS http://mcp-gw-istio.mcp-gateway-demo.svc/echo \
  | grep -vE 'x-envoy-peer-metadata|x-envoy-decorator'
# PASS evidence: the echoed request contains x-db-password and x-granted-scope
bash · RHGW-P5 (negative)
oc patch authconfig mcp-callout -n mcp-gateway-demo --type=json \
  -p '[{"op":"replace","path":"/spec/authorization/allowed/patternMatching/patterns/0/value","value":"deny"}]'
sleep 20    # propagation; an immediate check can race
curl -sS -o /dev/null -w 'HTTP %{http_code}\n' http://mcp-gw-istio.mcp-gateway-demo.svc/echo
# PASS evidence: HTTP 403
oc patch authconfig mcp-callout -n mcp-gateway-demo --type=json \
  -p '[{"op":"replace","path":"/spec/authorization/allowed/patternMatching/patterns/0/value","value":"allow"}]'
Validate before you continue

Both evidence strings captured: injected headers present on the positive leg, HTTP 403 on the mismatch leg, and the patch reverted (re-run the positive leg once more to prove the revert took). If a probe dies mid-run, remember it may have left the AuthConfig in the deny state.

Part 3

The IBM decision plane

The spike proved the seam. Now replace the stand-in with the real policy decision point, federate real MCP servers behind the broker, and move the AuthConfig onto the MCP path. This is where every hard-won routing and expression-language lesson lives; read the field notes even if you skip the prose.

8

Deploy the policy service

Manifests: deploy/rhgw/08-policy-service.yaml · 08b-policy-service-subagent.yaml · source: policy-service/src/server.js

The policy service is deliberately boring: one Node 20 file, zero npm dependencies, built-in fetch and http only. A policy decision point should be auditable in one sitting. It exposes five routes on its main listener (default port 8090): POST /authorize, POST /hitl/complete, POST /lease/revoke, GET /me/audit, and GET /healthz, plus a second listener (8092) that serves only revoke and health, which matters in step 13.

On every tools/call, /authorize runs this chain, denying at the first failure:

  1. Parse the Authorino body parameters (the caller's bearer, the raw MCP JSON-RPC body, the optional user email).
  2. Allow non-tool-call methods (initialize, notifications/*, tools/list) as not_a_tool_call, and the broker's own meta-tools (discover_tools, select_tools, filter_tools_by_tags, list_tags) as broker_meta_tool. No credential is minted for either.
  3. Strip the federation prefix (TOOL_PREFIX), resolve the tool in tools.json for its tier and action, map the action through rar.json for a credentials path. Unknown tool, unmapped action, and tier-4 tools deny here, locally, before any external call.
  4. Build the RFC 9396 authorization_details from the tool and its arguments, including dual-shape vault:path_access legs (both path_constraint/action and path/capabilities, because Vault Enterprise builds read different field names).
  5. Log in to Vault (Kubernetes auth, fresh each call), mint the gateway's own actor SVID.
  6. Run one RFC 8693 exchange at Verify: subject token = the caller's bearer, actor token = the SVID, plus the RAR and scope. Verify evaluates its access policy against the requested details and stamps the act claim.
  7. If Verify answers mfa_challenge, park the transaction and deny with step_up_required and a transaction id (step 12).
  8. Otherwise, for actions carrying a credentials path, present the exchanged token itself to Vault as X-Vault-Token and mint the ephemeral credential (lease TTL 300 seconds), answering decision: allow with the credential, username, scope, and lease id. Static-credential tools (Jira, GitLab) run the same decision but get a decision-only allow with no credential fields; their thin MCPs hold their own vendor tokens.
Contract with Authorino: a deny is HTTP 200

Authorino treats a non-2xx metadata response as an evaluator failure, which is a different and far less legible thing than a policy decision. The policy service always answers 200 with decision: "allow" or decision: "deny" plus a reason, and the AuthConfig gates on the decision field. Keep this contract in your own implementation.

The Deployment's load-bearing configuration, with every environment variable named. Secret values arrive by Secret reference and the tool/RAR config by ConfigMap; nothing sensitive is inline:

yaml · 08-policy-service.yaml (trimmed)
spec:

                                         # actor SVID, release verify-rar/creds/*, revoke a lease
  containers:
    - name: policy
      image: image-registry.openshift-image-registry.svc:5000/mcp-gateway-demo/policy-service@sha256:...
      ports: [{containerPort: 8090}]
      env:
        - {name: PORT,                    value: "8090"}
        - {name: VAULT_ADDR,              value: "http://vault.vault.svc:8200"}
        - {name: VAULT_ROLE,              value: "mcp-gateway"}
        - {name: VERIFY_TENANT_URL,       value: "https://your-tenant.verify.ibm.com"}
        - {name: GATEWAY_ACTOR_TOKEN_TYPE, value: "PocGatewaySPIFFE"}
        - {name: GATEWAY_SPIFFE_MINT_ROLE, value: "mcp-gateway-demo"}
        - {name: CONFIG_DIR,              value: "/config"}
        - {name: TOOL_PREFIX,             value: "dbx"}
      envFrom:

  volumes:

Demo-only escalation

The POC manifests set POLICY_DEBUG_OBO=true, which puts the raw exchanged token (a Vault-accepted credential for its five-minute life) into the audit ring so a demo can decode the signed-in RAR. The code's default is off. Never set it outside a demo.

Two deployments of the same image give you tiered identity: the parent (08) and a read-only subagent variant (08b) that differs in three identity-relevant ways: a different SPIFFE mint role (so every released credential is attributed act: reader-subagent), a different Verify exchange application's secret, and a read-only tool config in which write and delete tools simply do not exist (they resolve unknown_tool before any exchange runs; the config ships at gateway/config/databricks-subagent/). It also carries two operational deltas: an optional, commented node anti-affinity example for keeping it off a CPU-pressured worker, and a Service exposing only 8090, with no revoke port.

Validate before you continue

Exercise /authorize directly, one call per enforcement branch, so a failure here is distinguishable from a failure in the Envoy or Authorino plumbing around it. The probe script sets up its own oc port-forward when POLICY_URL is unset, so it runs from a workstation as-is (the in-cluster DNS name does not resolve from your laptop; set POLICY_URL yourself only to override the target):

bash · RHGW-P7, five branches
bash scripts/probe-policy-service.sh
# PASS evidence, branch by branch:
#   dbxdatabricks_query   -> decision allow, WITH a real credential (redacted in output)
#   dbxdatabricks_write   -> deny: Verify refuses the unapproved write
#   dbxdatabricks_delete  -> deny: refused locally, tier 4, before any external call
#   dbxnot_a_tool         -> deny: unknown_tool
#   tools/list (no auth)  -> allow: not_a_tool_call (asserted, because silently
#                            allowing everything would look identical to a broken policy)

The tier-3 write branch's shape depends on the subject: a real human subject draws mfa_challenge (approvable, step 12); a client_credentials service subject is refused outright because there is nobody to challenge. Both are correct refusals of an unapproved write; the probe prints which subject it used so you never have to guess.

Federate MCP servers behind the broker

Manifests: deploy/rhgw/07-mcp-federation.yaml · 11-mcp-federation-jira-gitlab.yaml · probe: scripts/probe-rhgw-mcp.sh

Federation is one MCPGatewayExtension per gateway namespace plus an HTTPRoute and an MCPServerRegistration per upstream (the first manifest carries all three for Databricks; the second adds only the per-upstream pairs for Jira and GitLab). The extension is what makes the operator deploy the broker-router and write an EnvoyFilter against your Gateway; you never name a broker image yourself.

If you have no real MCP upstreams yet, oc apply -f deploy/rhgw/07b-mock-backends.yaml deploys mock Databricks, Jira, and GitLab servers behind the exact Service names and ports the federation manifests reference. The mocks are minimal JSON-RPC responders: enough for federation discovery and every authorization checkpoint in this guide (the Databricks mock even returns the seeded revenue cell the end-to-end probe string-matches), but they implement no Mcp-Session-Id handling, so the stateful-session requirement in the field note below still applies in full to any real upstream you swap in.

                                   # finds the route and then silently stops

  rules:
    - matches: [{path: {type: PathPrefix, value: /mcp}}]
      backendRefs: [{name: databricks-mcp, port: 5113}]

  name: databricks-mcp
  namespace: mcp-gateway-demo

  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute

  path: /mcp
  prefix: dbx                    # concatenated with NO separator: databricks_query

---

  namespace: mcp-gateway-demo
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: Gateway

Learned live: four ways this silently half-works
  • Hostname collision. If an upstream route's hostname equals the extension's publicHost, the router's rewritten hop matches the broker's own route and every authorized call fails with "tool not found" while tools/list keeps advertising the tools. Distinct hostname per upstream, always.
  • Missing sectionName. The route attaches to the Gateway generally, the controller logs that it found it, then writes nothing into the broker config and sets no status condition at all.
  • Missing route hostname. Fine as a plain route, but the registration fails with "must have at least one hostname". The hostname is synthetic; no external DNS is involved.
  • Stateless upstream sessions. If your thin MCP runs the SDK's stateless Streamable HTTP mode, the broker's long-lived registration stream gets a 404 and its routing table stays empty. Run real sessions (sessionIdGenerator, GET and DELETE handlers).

Authorize the MCP path

Manifest: deploy/rhgw/09-mcp-authconfig.yaml · probe: scripts/probe-rhgw-authz.sh

Now move authorization from the spike's echo path onto the real MCP path. Before the YAML, one empirically learned ordering fact that decides two of its fields, because getting either wrong does not fail loudly: it silently exempts exactly the tool calls from authorization.

The manifest creates two objects. First, the AuthorizationPolicy that step 7's manifest created with /echo* only: this file re-declares the same object extended to both paths and owns it from here on (which is why step 7 carries the never-re-apply-06-after-this warning):

Second, the production AuthConfig. Its shape is the spike's, with three load-bearing differences: the hosts list covers the public and all upstream hostnames, the callout POSTs the caller's bearer and the whole MCP body to the policy service, and the deny response carries the callout's JSON to the caller.

yaml · 09-mcp-authconfig.yaml (object 2)
apiVersion: authorino.kuadrant.io/v1beta3
kind: AuthConfig
metadata:
  name: mcp-tool-authorization
  namespace: mcp-gateway-demo
spec:
  hosts:
    - mcp.gateway.internal              # the public host (initialize, tools/list)
    - databricks-mcp.gateway.internal   # every upstream host (rewritten tool calls)
    - jira-mcp.gateway.internal
    - gitlab-mcp.gateway.internal
  authentication:
    anonymous:
      anonymous: {}                   # still anonymous, replaced in step 11
  metadata:
    policy:
      http:
        url: http://policy-service.mcp-gateway-demo.svc:8090/authorize
        method: POST
        contentType: application/json
        bodyParameters:
          authorization:
            selector: context.request.http.headers.authorization
          mcp:
            expression: 'request.body'          # safe: field access, empty when absent
          userEmail:
            selector: context.request.http.headers.x-user-email
  authorization:
    allowed:
      patternMatching:
        patterns:
          - selector: auth.metadata.policy.decision
            operator: eq
            value: allow
  response:
    success:
      headers:
        x-db-password: { plain: { selector: auth.metadata.policy.credential } }
        x-db-username: { plain: { selector: auth.metadata.policy.username } }
        x-granted-scope: { plain: { selector: auth.metadata.policy.scope } }
    unauthorized:
      code: 403
      message:
        selector: auth.metadata.policy.reason   # becomes X-Ext-Auth-Reason, never the body
      body:
        selector: auth.metadata.policy          # the callout JSON, verbatim, as the 403 body:
                                                # this is how a step-up txId reaches the caller
Selectors, not CEL, for optional headers

In bodyParameters, a CEL map index on an absent header (expression: 'request.headers["x-user-email"]') throws "no such key", and Authorino treats one failed parameter as failure of the entire metadata evaluator: the callout is never sent, the metadata object goes missing, and every request dies as a 403 with an empty body and a blank reason header. This took the composed path down in the POC for any caller not sending the header, and nothing at default log level pointed at the cause. Selectors (context.request.http.headers.*) resolve missing paths to empty. If you must use CEL, guard it: '"x" in request.headers ? request.headers["x"] : ""'.

Learned live: single ownership

The spike's manifest (step 7) deliberately carries the /echo*-only copy of this AuthorizationPolicy so the seam is provable before the MCP path exists. From this step on, this file owns the object. Re-applying the spike's copy after this one reverts the rule, oc apply says "configured" both times, and the only symptom is that the callout stops being invoked for MCP while every object looks healthy. That exact failure happened live in the build this guide is drawn from: apply 06 before 09, never after.

Validate before you continue

12

Step-up approval over a synchronous callout

Source: policy-service/src/server.js (park, complete, redeem) · probe: scripts/probe-hitl-callout.sh

A tier-3 write needs a human to approve a real emailed one-time code. The structural problem: an ext_authz callout answers synchronously and cannot hold a connection open across a human's round trip to their inbox. The answer is park-and-retry: the step-up parks approval state in the policy service, the deny carries a transaction id to the caller, and the agent's retry of the identical call redeems the approval.

Implementation facts that carry the security properties, all enforced in policy-service/src/server.js:

  • The park is owner-bound. /hitl/complete resolves the caller's sub via Verify userinfo and refuses completion unless it equals the parked owner's. A wrong code re-parks under the same transaction (otp_invalid); an expired code is otp_expired; an unknown transaction id is refused.
  • Leg 2 must re-send the RAR. Verify does not propagate authorization_details across exchange legs, so the parked context stores them and the jwt-bearer exchange sends them again. Forget this and the elevated token authorizes nothing.
  • The email destination comes from the request context (the x-user-email body parameter first, then the userinfo email claim). This is exactly the optional header from step 10's CEL warning: the absence-safe selector is what keeps email-less callers deniable rather than crashing the callout.
  • The redeem window is tight. The park lives five minutes, the elevated approval 60 seconds, keyed sub | tool | argsHash: only the same person retrying the same tool with the same arguments redeems it.

Restore post-use revoke, on a separate listener

Manifest: deploy/rhgw/08-policy-service.yaml (Service ports) · tests: tests/check_lease_revoke.sh

A 300-second lease is short, but revoke-after-use is shorter. The composed path initially accepted TTL-only expiry as a trade-off; it was corrected by adding a revoke-only listener on a second policy-service port (8092) that serves exactly POST /lease/revoke and /healthz. The agent runtime drives a revoke through it after each proxied call returns.

Why a second port instead of opening the main one: /authorize returns minted credentials to its caller, and per the callout design it trusts network reachability as its authentication. Opening 8090 to the sandboxed agent would hand a prompt-injected agent the credential channel. The sandbox's NetworkPolicy therefore opens only 8092, and the revoke handler is safe by construction:

  • The bearer is validated via userinfo, and the lookup key is the token's own sub claim: a caller can only ever reach its own user's mints.
  • The lease id is never accepted from the caller (an arbitrary-id revoke endpoint is a denial-of-service primitive). The service looks up its own recorded mint.
  • Each record is single-use, and the revoke runs against Vault with the recorded exchange token, whose RAR carries the sys/leases/revoke grant.
  • Vault refusal is reported honestly (revoked: false, 502), never masked as success.

The habits that made this debuggable
  • A verdict is a claim; the capture is the evidence. The POC's recorder happily writes PASS over an empty capture if the author says so. Whatever harness you build, read the output, not the label.
  • A model's narration is not evidence either. The origin demo caught a sandboxed agent fluently describing commands it never ran. Only a real tool-call and result pair, read from raw logs, proves execution. The same skepticism applies to your own probes.
  • Prove reverts. Three checkpoints in this guide mutate live objects and restore them. The restore is a claim too: re-run the positive leg after it.
